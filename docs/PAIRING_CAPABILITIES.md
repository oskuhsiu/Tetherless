# Pairing capability and cancellation boundary

Reviewed 2026-10-05 against Tetherless `3dd8641e84698b97f96d53a6c53ed8c6ca4675bd`, SideStore `0dd743f75afc358b0ba4a002feb5f19474492371`, and minimuxer `12be70dc2627307a16bfd2dc7a009080d5bec909`. The safety increment described below is a temporary gate, **not completion of PAIR-01 or AUTO-02**.

## Actual capability versus product support

Apple's current Device Hub documentation requires iOS/iPadOS 27 or later for first-time wireless iPhone/iPad pairing; older systems use a cable. Apple announced availability of iOS 27 on September 14, 2026. Thus iOS 27 is an available platform at this review date, not a future-version assumption. Those sources establish Apple's Mac/device workflow, not Tetherless same-phone success. [Apple Device Hub](https://developer.apple.com/documentation/xcode/pairing-your-devices-with-your-mac), [Apple availability](https://www.apple.com/newsroom/2026/09/major-updates-for-apples-software-platforms-are-now-available/)

The exact minimuxer README also advertises iOS 27+ wireless pairing. Its actual Swift public API has no iOS 27 availability check. SideStore's advanced-settings screen does not gate iPhone support by OS, device role or gateway backend; the iOS 16 checks in its view only control sheet presentation. The libimobiledevice backend explicitly rejects both wireless operations. These checks must be part of a future product capability decision; the library's deployment target is not a statement of wireless support. [Pinned README](https://github.com/SideStore/minimuxer/blob/12be70dc2627307a16bfd2dc7a009080d5bec909/README.md), [public API](https://github.com/SideStore/minimuxer/blob/12be70dc2627307a16bfd2dc7a009080d5bec909/Sources/MinimuxerApi.swift), [unsupported gateway](https://github.com/SideStore/minimuxer/blob/12be70dc2627307a16bfd2dc7a009080d5bec909/DeviceGateway/libimobiledevice/LibimobiledeviceGateway.swift)

| Route | Exact behavior | Current Tetherless evidence/status |
| --- | --- | --- |
| Import an existing record | Parse lockdown/remote plist and copy into protected storage | Implemented. Parser/storage tests do not establish a live device connection. Selected-file system-picker UI remains unresolved separately |
| Wireless host, `start` | Advertise a pairable host; device Settings initiates pairing; `onPinReceived` supplies the code displayed by the host | Temporarily gated before native work because cancellation is unsafe in the pinned adapter |
| Wireless client, `trigger` | Connect to a selected target; `onRequestPin` asks for the code shown on that target | Temporarily gated. This Apple TV/other-device role is unnecessary for the primary same-phone iPhone host workflow |
| Clean-phone first install | Deliver, sign and install a runnable manager before it can pair | BOOT-01 remains separate research; neither import nor generated pairing provides app delivery |

Tetherless onboarding currently exposes only import. It does not call `wirelessPairing.start` or provide a same-phone Settings/PIN lifecycle. Its readiness model correctly distinguishes stored prerequisites, explicit renewal permission, live renewal and observed non-foreground evidence. The permission toggle is not proof of a configured Shortcut or unattended renewal. `NativeRenewalRuntime.confirmRepair()` performs live preflight before clearing repair gates; importing a plist must not substitute for that check.

## Verified safety failures in the baseline

1. **Stop does not join the native operation.** `WirelessPairService.stop()` cancels Swift tasks and stops advertising. `IdeviceGateway.startWirelessPair` delegates synchronous blocking `TCPAcceptor.accept()` and `pairable_host_accept_fd` through `withFFIDispatch`, which has no cancellation handler. The Swift task flag neither closes the socket nor interrupts FFI. Tetherless deliberately keeps the session's process lease alive until the callback returns, so an abandoned server can keep renewal/reset busy indefinitely. Releasing the lease on a timer would reintroduce concurrent device mutations. [Service](https://github.com/SideStore/minimuxer/blob/12be70dc2627307a16bfd2dc7a009080d5bec909/Sources/Services/WirelessPairService.swift), [gateway](https://github.com/SideStore/minimuxer/blob/12be70dc2627307a16bfd2dc7a009080d5bec909/DeviceGateway/idevice/IdeviceGateway.swift), [acceptor](https://github.com/SideStore/minimuxer/blob/12be70dc2627307a16bfd2dc7a009080d5bec909/Common/TCPAcceptor.swift), [FFI dispatch](https://github.com/SideStore/minimuxer/blob/12be70dc2627307a16bfd2dc7a009080d5bec909/Common/FFIDispatcher.swift)

2. **Client cancellation can become a fabricated PIN.** The Swift gateway waits up to 60 seconds for a PIN. Tetherless's existing Cancel clears the callback and stops the Swift task, but cannot interrupt that wait. At the pinned idevice source, `rppairing_pair_network` has no cancellation argument or exposed connection handle. Its `get_pin` converts a null callback result into `000000`. Returning null or waiting out the prompt is therefore not cancellation. [Pinned FFI](https://github.com/SideStore/idevice/blob/3e55c8486b2057e40c1f74aaaa1155c82341cf76/ffi/src/tunnel_provider.rs)

3. **PINs reach unconditional loggers.** The service logs the generated PIN, and the gateway logs the displayed and entered PIN. `debugLog` prints irrespective of `setLogging(false)`; `verboseLog` also exposes the displayed code when enabled. Removing view-model logs alone does not close these sinks. [Minimuxer logger](https://github.com/SideStore/minimuxer/blob/12be70dc2627307a16bfd2dc7a009080d5bec909/Sources/MinimuxerLogging.swift), [gateway logger](https://github.com/SideStore/minimuxer/blob/12be70dc2627307a16bfd2dc7a009080d5bec909/DeviceGateway/DeviceGatewayLogging.swift)

4. **Lifecycle and replacement are incomplete.** The inherited view's `onDisappear` only logs. PIN/ready/request callbacks are not session-generation-scoped, although Tetherless protects the final completion with session identity. There is no same-phone PIN presentation while Settings is foregrounded, bounded user-initiated background lifetime, or stale-callback/teardown test. Successful wireless import immediately promotes the remote record and removes the other protocol record; it does not first prove that the paired peer is the current phone. The generic target picker can pair another device. [View](https://github.com/SideStore/SideStore/blob/0dd743f75afc358b0ba4a002feb5f19474492371/SideStore/Views/Settings/Advanced/PairingFile/WirelessPair/WirelessPairView.swift), [model](https://github.com/SideStore/SideStore/blob/0dd743f75afc358b0ba4a002feb5f19474492371/SideStore/Views/Settings/Advanced/PairingFile/WirelessPair/WirelessPairViewModel.swift)

## This bounded safety increment

`Integration/pairing_safety.py` checks four exact Git blob preimages before writing any transformed output. The model and wrapper preimages are the actual outputs of `input_safety.py`; the minimuxer preimages are the pinned original sources.

- Replace all three identified lower-layer PIN interpolations with fixed, value-free messages. PIN delivery to the actual protocol/UI callback is unchanged
- Reject both wireless roles in the view-model before discovery, session/lease allocation, staging or native calls; show an explicit unavailable message
- Reject both methods at the product wrapper as defense in depth, returning failure exactly once and never calling the filename resolver
- Preserve imported records, import UI, reset semantics, existing renewal consent and the normal renewal path
- Do not manufacture success, fake a PIN, add a timeout that releases a live worker's lease, or claim the cancelled worker has stopped

Nine focused tests cover source drift, transformed preimages, all-input validation before writing, reapplication, entry-point gating, protocol callback preservation and production chain wiring. Two are executable Swift tests: repeated wrapper failure with a resolver that must never run, and synthetic PIN sentinels passed through the exact transformed statements with both actual upstream logger implementations in both logging modes. A missing Swift compiler is reported as a skip, not a pass. This does not audit every binary logger or establish a native pairing handshake.

## Next viable same-phone adapter increment

The pinned idevice source already exports `pairable_host_cancel_new`, `pairable_host_cancel_signal`, `pairable_host_cancel_free`, and `pairable_host_accept` / `pairable_host_accept_with_options`. Their cancellation token covers both waiting for a connection and the async handshake. The implementation checks cancellation before starting, selects cancellation against the pairing future, then shuts down mDNS before returning. This is a promising existing native boundary, not a need to invent a timeout. [Cancellable host source](https://github.com/SideStore/idevice/blob/3e55c8486b2057e40c1f74aaaa1155c82341cf76/ffi/src/pairable_host.rs)

The current minimuxer adapter instead uses `pairable_host_prepare` + its own Swift `NetService` + `pairable_host_accept_fd`. The latter duplicates the supplied socket and preserves caller ownership, so an explicitly owned socket shutdown adapter is another candidate. The cancellable combined API uses Rust `mdns_sd`; adopting it changes discovery/local-network behavior and has no matching `onReady` callback. It must not be silently treated as equivalent to the current NetService path. [Current FD contract](https://github.com/SideStore/idevice/blob/3e55c8486b2057e40c1f74aaaa1155c82341cf76/ffi/src/pairing_host.rs)

The package pins the XCFramework ZIP SHA-256 `445702d53942597deb4cdec2c4122d16a3f4ac124ce26cd75b68dab3dad92416`; the GitHub release asset's digest matches and its release targets the source commit above. At the original source-review checkpoint, actual packaged symbols and generated headers had not been inspected; the later observation below supersedes that evidence gap. A matching release digest identifies bytes; it does not prove exported symbols or binary/source equivalence. [Package](https://github.com/SideStore/minimuxer/blob/12be70dc2627307a16bfd2dc7a009080d5bec909/DeviceGateway/Package.swift), [release](https://github.com/SideStore/idevice/releases/tag/v0.1.68-ss-3e55c84)

The native-build workflow now includes a read-only packaged-API observation after compilation. `Integration/inspect_pairing_api.py` inspects the existing resolved IDevice XCFramework with Apple `file`/`nm`, records textual header declarations and defined exports separately for each declared iOS device/simulator architecture, and saves `artifacts/pairing-api-<configuration>.json`. Missing surfaces, bounded-output truncation and tool failures remain incomplete evidence. This does not execute the packaged library, change package pins, enable wireless pairing, prove ABI/link compatibility, or authenticate binary/source provenance. The evidence step cannot replace the build result; the actual inspected observation is recorded below.

## Actual packaged observation at d566891

[Native run 37294413252](https://github.com/oskuhsiu/Tetherless/actions/runs/37294413252), source `d5668911cb60564f4b217093deb5da4e83862b67`, built and packaged both Debug and Release successfully. Both outer artifact digests were independently verified; their packaged-API reports contain identical observations. Both the device and Simulator arm64 slices contain textual declarations for all four required host/cancellation functions and optional `pairable_host_accept_with_options`. The actual header SHA-256 is `23e7ab332fc73788b67b441b0c128720f3ddbd2210672cbc4bcb1503b5ca8426` in both slices.

- Device static archive SHA-256: `622e8f91aa285bf1a6076e2853da9cacb39839bfd72ad1b1b08a0902e7f33d5b`
- Simulator static archive SHA-256: `83e94401faf680916740ba112c630e0e52bbfc98ef0d77b53967494b63858f23`

The selected Xcode `nm` failed with unknown LLVM attribute errors while reading Rust compiler-builtins archive members (producer LLVM 22.1.8, Apple reader LLVM 17). The reports therefore correctly remain `inspection_status: incomplete`. Empty `defined_exports` and populated `missing_exports` after that failed command **do not establish absent symbols**. Successful compilation of the existing app does not prove that these previously unused functions compile and link. The next narrow observation is an actual typed C/Swift compile-and-link check against these exact artifacts; its outputs must never be executed by the diagnostic. No linker, ABI-runtime, cancellation or handshake pass is claimed yet.

A separate promotion gap also remains: the existing live-UDID lookup identifies the connected peer and updates a local cache. It does not independently establish that a newly staged record belongs to the current phone. Neither that mutable cache nor successful PIN exchange alone may authorize automatic replacement of the prior usable record. Both existing product gates remain in place; imported/stored-record and normal renewal routes are unchanged.

Before removing the gate:

1. Inspect the exact packaged headers and each used architecture's exports for the four host/cancel functions. Compile/link the adapter against that artifact; do not assume source declarations prove binary availability
2. Prefer the device-initiated host role only. Keep the client role disabled until its own native cancellation contract exists; it is not needed to achieve same-phone iPhone pairing
3. Own the token and PIN callback context until native completion. Cancel by signalling the real native operation, retain the mutation lease while joining it, and free the token/staging only after quiescence. Use request generations for every callback, including PIN and ready
4. Test cancellation before start, while accepting, during PIN exchange, concurrently with success, on view dismissal and during background expiration. Test repeated start/cancel/re-pair; prove no late commit, no leaked socket/worker/lease and no fabricated PIN
5. Add OS/backend/simulator checks and explicit local-network/Developer Mode guidance. Provide a legitimate user-initiated lifetime and a way to see the PIN while switching to Settings. Do not add fake audio/location keepalive or borrow daily background scheduling as proof
6. Keep a replacement record staged until explicit same-phone pairing and live validation succeed. Preserve the prior usable record on denial, invalid data, storage failure, wrong peer or cancellation; do not automatically clear account or renewal consent
7. Connect this bounded controller to onboarding and repair. Confirm live channel/account readiness separately; ordinary unattended work must return `needsPairing` when interaction is needed

## AUTO-02 and BOOT-01 remain separate

The system document-picker selected-file failure remains its own acceptance condition; a gated wireless path does not fix it. Valid and invalid import, two consecutive cancels, source-file preservation, protected-store retention, relaunch, denied login/2FA/local network/notification permission, explicit renewal permission and a real non-foreground renewal observation all remain distinct checks. No live Apple credentials or phone were used for this review.

Clean-phone bootstrap is not established by wireless pairing. Apple's Ad Hoc workflow requires an App ID, a distribution certificate and registered devices; that is a bounded distribution option, not evidence of a general free-account browser installation chain. Keep initial trusted delivery and same-Team/changed-Team manager recovery separate from ordinary phone-only renewal. [Apple Ad Hoc requirements](https://developer.apple.com/help/account/provisioning-profiles/create-an-ad-hoc-provisioning-profile/)
